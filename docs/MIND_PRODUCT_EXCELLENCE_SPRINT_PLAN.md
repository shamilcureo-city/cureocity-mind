# Mind product excellence — detailed sprint plan

Prepared 13 September 2026. **Proposal only: no implementation, merge, migration, deployment or clinical-content approval is authorized by this document.**

## 1. Owner decision

Build one dependable psychologist journey before expanding the therapy catalog:

**Prepare once → stay with the client → review an accurate note → agree the next step → pick up where you left off.**

The product promise is: “Mind helps me stay present, finish documentation quickly, and enter the next session prepared.” Success is measured by less work and trustworthy continuity, not number of tabs, generated words, selected therapies or time spent in the software.

This plan covers the 12 September product assessment: documentation, UI/UX, capture, assessment/diagnostic support, therapy depth, continuity, cost and real-use validation. Mind remains psychologist-specific. Scribe receives shared-code regression protection, not a new doctor-product roadmap. Marketing, sales, payment redesign and autonomous AI counselling are out of scope.

## 2. Scope, capacity and responsibilities

### Must, should, later

- **Must before the affected feature is released:** truthful capture/save state; no known contaminated source signed or reused as clinical evidence; recovery and privacy boundaries; consistent therapy-entry invariants; clinician authority; reproducible verification; compatible rollback.
- **Should in this programme:** one preparation flow, source-aware note review, less duplicate entry, a small reviewed therapy pathway, meaningful next-visit context and full-session AI accounting.
- **Later, separately gated:** additional reviewed pathways, additional authorized questionnaire languages/instruments, specialty populations and richer practice analytics.
- **Not in this programme:** “all therapies”; autonomous diagnosis, treatment, referral or discharge; AI-created scored questionnaire translations; clinical-decision streaks; a new parallel dashboard; changing Scribe into Mind; silent repairs to signed historical records.

### Working assumptions, not deadlines

- Assume one AI-assisted engineering stream, a product/design owner, part-time qualified psychologist review, and language review when required. These are roles, not confirmed staffing. AI assistance does not replace clinical approval.
- MP00 is a short stabilization timebox, provisionally one week. MP01–MP09 are provisionally two-week planning slots: six build days, two verification/review days and two contingency days per slot.
- This is **19 weeks of nominal slots, not a promised completion date or a total-effort estimate**. Each numbered sprint is an outcome package; split it before commitment if refinement exceeds capacity. MP01, MP03, MP04, MP06, MP07 and MP08 are especially likely to need additional iterations or external review time. Re-estimate after MP00 and MP01. Commit only a minimum independently demonstrable slice that fits the available build days.
- Commit one sprint at a time. Clinical-content selection, benchmark preparation and scheduled clinician observations begin during MP00 and continue alongside engineering. Do not run several implementation streams on assumed one-person capacity.
- When capacity is short, reduce optional content or split an outcome; do not remove a safety or verification gate. The later sprints are detailed candidates, not frozen commitments.

| Role                     | Responsibility                                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Product owner (PO)       | Scope, intended users, workflow decisions, priority trade-offs, acceptance of user-visible behaviour                          |
| Engineering (ENG)        | Contracts, UI/API/storage, automated tests, instrumentation and release evidence                                              |

| Language reviewer (LANG) | Malayalam/English semantic fidelity and authorized localized content; separate instrument-validation requirements still apply |

Names, available hours and conflicts must be recorded at kickoff. PO owns obtaining missing reviewers. Missing clinical approval blocks publishing that clinical content, not generic engineering using clearly fictional fixtures.

## 14. Product metrics and provisional gates

These are **proposed engineering/product acceptance targets, not achieved results, statistical population guarantees or clinical cutoffs**. Lock definitions and thresholds before running a held-out release evaluation; record any change and its reason. Numeric success cannot override a critical safety/privacy failure or clinical-review veto.

An empty dataset, zero applicable denominator, mock-only run or missing required billing evidence reports **not evaluated**, never a pass. Record dataset hashes, model/prompt versions, web/gateway revisions and configuration with each result. Raw audio/transcripts stay in authorized protected evaluation storage, not Git or ordinary telemetry. ## 15. Definition of done and release boundaries

Every ticket includes a user-visible demo, happy-path and failure-path tests, current documentation and a recorded reviewer. Every sprint includes relevant keyboard/accessibility checks and the necessary clinician review—not just screenshots and unit counts.

For changes touching clinical data: owner/capability checks, consent boundaries, encryption, version conflict handling, idempotency, erasure races, DSR export/erasure coverage and safe telemetry are part of the ticket. No new plaintext browser clinical persistence. Signing, sharing, booking, referral and episode changes retain their explicit authority boundaries.

Release evidence must distinguish:

1. Local implementation and automated checks.
2. Commit/PR review and current-main compatibility.
3. Database migration readiness, if a schema change is actually needed.
4. Web deployment/readiness.
5. Separate standalone live-gateway image/configuration/traffic readiness.
6. Authorized real browser/device/auth/encryption checks.
7. Qualified clinical-content and real-use validation.

One does not prove the next. Obtain explicit approval for the exact production target and changes before side effects. Use small reversible releases and feature flags where appropriate; never disable consent, privacy or clinical safety checks to pass a smoke test.

For the current transcript-format candidate, release the compatible web reader before the updated gateway and exercise old/new reader-writer compatibility. Generic release ordering alone is not that compatibility proof.

### Specific rollback constraint already known

The new encrypted transcript envelope requires a compatible web decoder. Once new-format transcripts exist, a rollback to an older reader can expose serialized JSON as transcript text. Preserve/backport the decoder in any rollback target. A gateway rollback alone can restore the old transcription defect; disable the affected live feature if necessary rather than accepting contaminated output. Never destructively rewrite clinical records to make rollback convenient. See the existing [transcript rollout notes](MIND_TRANSCRIPT_QUALITY_FIX.md).

New migrations in later sprints need separate design: additive compatibility, old/new reader tests, explicit data recovery strategy and verified production history. A code rollback is not a database rollback.
